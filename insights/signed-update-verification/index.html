A signature is not an update policy

An executable study of signed manifests, target checks, rollback rules and the bytes an installer actually consumes.

17 Nov 20266 min readNexaFusion

An executable engineering study using synthetic data. This is not client work, production firmware or a certification claim.

A valid signature is one decision.

Imagine a device receiving an update over a channel an attacker can control. Authenticity matters, but a correctly signed image can still belong to another board or contain an older, vulnerable version. An update admission decision needs to connect the signed metadata, the exact payload and trusted device state.

The trust boundary

The example assumes an attacker can replace, truncate, replay or alter the incoming manifest, payload and signature. The verifier receives a trusted public key, device identifier, installed version and minimum permitted version from its caller. An attacker who controls those trusted values is outside this model.

The manifest contains five fields: schema version, target device, release version, payload length and SHA-256 digest. ECDSA P-256 authenticates the exact UTF-8 manifest bytes. The implementation delegates cryptography to Web Crypto.

The demonstration defines one JSON encoding: those five fields in that order, with the compact serialization shown in the verifier. Duplicate keys, extra fields and alternate encodings are refused, avoiding disagreement between parsers about which value was authenticated. This encoding rule is part of this example’s format.

The admission sequence

  1. Require cryptographic verification and a valid trust context. Refuse the update if either is unavailable.
  2. Limit the manifest to 1 KiB, the demonstration payload to 1 MiB and the signature to 64 bytes before expensive work.
  3. Copy the input bytes and trusted state before the first asynchronous operation.
  4. Verify the manifest signature against the trusted key, then parse its bytes as strict UTF-8 and validate the supported schema.
  5. Check the target device and require a release newer than the installed version and no older than the minimum permitted version.
  6. Check the payload length and digest. Return the verified payload snapshot for the caller to consume.

A subtle failure: checking one buffer, using another

Verification is asynchronous. If the caller can change a shared input buffer while verification is pending, a successful check may refer to bytes that differ from the bytes later installed. This example snapshots the inputs and returns the verified payload. Its concurrency test changes the original buffers and context immediately after starting verification, then checks that the returned bytes remain the authenticated bytes.

An installer must use that returned snapshot. Copying inputs inside a verifier does not protect a caller that subsequently flashes an unrelated or mutable buffer.

Evidence you can reproduce

The test suite generates temporary signing keys in memory and exercises acceptance, signature and payload tampering, an unrelated public key, a different device, replay and rollback, the minimum-version floor, length mismatch, unknown fields, malformed JSON and UTF-8, size limits, missing trusted state, crypto failures and buffer mutation.

What this does not establish

This is an admission-check model, not a secure boot implementation. A production device still needs a protected trust anchor and version state, signing-key lifecycle management, authenticated recovery, power-failure-safe installation, boot-time verification and a design appropriate to its hardware. The illustrative size limits and rollback rule are explicit design choices, not universal firmware requirements.

It does not defend against a compromised browser, a compromised signing key, physical attacks or a caller that supplies attacker-controlled trust state. It also does not demonstrate CRA conformity. Those boundaries are part of the engineering evidence.

API references: W3C Web Cryptography API and the Node.js Web Crypto documentation.
